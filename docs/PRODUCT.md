# 产品说明

## 给谁用、解决什么问题

coding-pal 是 Claude Code 和 Codex 的插件，给不写代码、但要把软件做出来的人用，例如产品经理。

用户只做业务上的事：回答问题、确认、验收。Agent 负责全部技术判断，按固定的阶段推进，把进度记在项目里，换个会话也能接上。

它要解决的是：没有流程时，Agent 容易没问清就动手、做完不验证、改动互相覆盖、换会话后忘了做到哪；流程太重时，又会把时间和 token 花在走形式上。所以 coding-pal 按任务大小走不同的步骤，机械操作交给自带的小工具 pal，Agent 只做判断。

## 现在能做什么

- **按任务大小推进：** 小改动直接改、请用户看效果；需求类任务按需求、界面、方案、实现、验收推进，每个关键节点等用户确认。
- **多个任务同时进行：** 每个任务在自己的工作副本里改，互不影响；验收通过后依次合并到主线，同一时间只合并一个。
- **看板：** 每个项目一个本机网页，列出等用户处理的事、各任务的阶段和状态、待开始、待发布、最近发布；另有汇总所有项目的首页。看板由 pal 生成，没有手写区域。
- **子代理分工：** 实现员照实现方案写代码，验收员按需求说明逐条独立检查，高风险的方案由评审员把关。模型和档位有默认值，用户可以改。
- **验收网页：** 每次验收生成一份本机网页：一句话结论、用户要做的事和预计用时、"请你试"的几件事、验收员逐条的结果和证据。
- **发布：** 有发布流程的项目，用户说"发布"后，把已合并的任务一起发成一个版本：定版本号、写变更记录和发布说明、打标记，按授权推送并创建 GitHub Release。
- **AI 功能的检查：** 项目里有 AI 功能时，改到 AI 行为的任务要跑相关的 AI 案例；看板会提醒多久没做全面检查。

使用前提：项目在 git 仓库里；电脑上有 Python 3.9 以上（pal 用到；第一次用时检查并提示安装）。

## 主要流程

### 任务类型

| 类型 | 怎么判断 | 步骤 |
|---|---|---|
| 小改动 | 一两句话说清，做完马上能看效果 | 改动 → 验收（用户看效果，说"可以"）→ 合并 |
| 普通需求 | 要写需求说明才说得清 | 需求 → 界面（有界面才有）→ 方案 → 实现 → 验收 → 合并 |
| 复杂需求 | 涉及几块互不依赖的模块，最后要联调 | 同普通需求；实现时几个实现员并行，最后联调 |

批量改数据、对外发布/付款/发消息、涉及隐私、大范围重构属于高风险，方案要经过评审。Agent 判断类型后用一句话说明理由，用户可以改判；拿不准时按普通需求。有发布流程的项目，合并后还有"发布"阶段。

### 用户要回复的地方

- 需求说明：Agent 交付草稿后，用户确认才算。回答问题或说"按推荐"不算确认。
- 界面演示页：有界面的任务，Agent 做一个可点击的静态演示页，用户确认后才写方案。
- 方案开头一页：说明用户会看到什么、有哪些取舍和代价、要不要评审、谁来实现；用户无异议或回复"继续"才开始实现。
- 验收：用户明确说"验收通过"（小改动说"可以"），之后自动合并。
- 发布：用户说"发布"才发布和推送。

### 换会话接上

在项目里说"继续"，Agent 先运行 `pal status`，列出等用户处理和正在做的任务；在某个任务的工作副本里开会话，就直接接上那个任务。

## 关键规则

- **三条底线**（只有用户在对话里明确要求才放开）：不丢没合并的成果；没验证不说完成；用户没说"发布"不推送。
- **只有两类问题让流程停下等用户：** 会做出错误的东西；会造成难以挽回的损失（数据丢失、误删、不可逆的对外动作、隐私外泄）。其他问题记下或顺手改，允许以后返工。
- **验证按风险轻重：** 改到逻辑就补自动测试；需求类和高风险任务派验收员独立检查；小改动由主 Agent 自查；合并时跑项目检查；AI 案例只跑和这次改动相关的，全部关键案例只在用户要求"全面检查"时跑。
- **长期文档随任务一起改：** 产品说明、实现说明、决定记录、变更记录在任务分支里更新，合并只是 git 合并。任务文件夹、看板和临时文件只存本机。
- **coding-pal 不管的事：** 回复语言和语气、提交和命名习惯、仓库公开习惯、权限和沙箱、电脑环境。这些由用户的个人规则决定。
- **记忆：** 接入项目时建议关闭 Agent 记忆，免得旧习惯带进新会话。Claude Code 可以按项目关闭；Codex 只能全局关闭。

## 术语

主 Agent｜和用户对话的那个 Agent，推进任务、做技术判断、派子代理
实现员｜照实现方案写代码和测试的子代理，不提交
验收员｜只读的子代理，按需求说明逐条检查并附证据
评审员｜只读的子代理，只在高风险任务里检查方案会不会做错或造成难以挽回的损失
工作副本｜每个任务自己的项目文件夹（`.worktrees/<任务>`），有自己的分支
卡片｜每个任务的进度记录：类型、阶段、状态、等用户做什么、下一步
阶段｜任务做到哪一步：需求、界面、方案、实现、验收、合并、发布（小改动是改动、验收、合并、发布）
状态｜现在轮到谁：Agent 在做、等你、暂停、排队（只在合并阶段）、待发布（只在发布阶段）
待开始｜用户提过、还没开始做的事
AI 案例｜项目里保存的一组输入，以及 AI "应该怎样、不能怎样"的说明
改到 AI 行为｜改了提示词、技能或子代理说明、工具设置、模型及参数、检索资料
全面检查｜跑项目全部关键 AI 案例，只在用户要求时做
