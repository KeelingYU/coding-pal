# 决定记录

用户做的业务决定，一行一条：日期｜决定｜理由。改变已确认的内容时，也记在这里。1.0.0 之前的完整记录在 Git 历史里（`docs/decisions.md`）。

## 产品定位

2026-08-03｜面向个人本地使用，不做团队、云端、企业级控制｜个人工具。
2026-09-12｜Agent 向用户汇报和请求确认时只讲业务影响，技术风险要翻译成后果，不能省略；交付给其他使用者时同样如此｜用户是产品经理，只做业务判断。
2026-09-13｜控制力度和出错的损失相称：允许有界、能发现、能恢复的错误，返工是可接受的成本｜过度追求一次做对会让项目长期卡在前期。
2026-10-09｜重建为 1.0：不兼容旧的文件布局，不做迁移工具｜旧版规则只加不减，任务又慢又贵；旧项目主要用于测试。
2026-10-09｜Claude Code 和 Codex 都正式支持；中文为主｜用户 10-09 确认重建方案时选定。
2026-10-11｜coding-pal 不管回复语言，不在技能或发布说明里要求用中文｜使用者也可能用英文。
2026-10-10｜coding-pal 不管权限、沙箱和"浏览器截图怎样免授权"，技能里也不写｜面向不懂技术的用户，插件不该干预或绕过用户选的权限模式。

## 流程

2026-10-10｜任务类型叫小改动、普通需求、复杂需求；阶段只管做到哪一步，状态只管现在轮到谁（Agent 在做、等你、暂停、排队、待发布）；"待开始"是用户提过、还没开始的事｜"需求"和第一个阶段重名；阶段和状态各管一件事，用户看过看板页面后定下。
2026-10-11｜小改动也在自己的工作副本里改；只有项目第一个版本在主文件夹做，它合并前不开新任务｜直接改主线时，没验收的改动可能被一起发布、放弃时难撤回、转成需求还要搬位置。
2026-10-09｜用户说"验收通过"即自动合并；用户说"发布"才发布｜合并只是保存成果，发布才对外。
2026-10-11｜项目发不发布版本在接入时和用户确认；不发布的项目合并即完成｜有的项目只在本机用，不发版本。
2026-10-09｜任务文件夹（卡片、需求说明、实现方案）只存本机；长期文档只有产品说明、实现说明、决定记录、变更记录 4 份；不再生成 CLAUDE.md；取消方案理解检查和"过程文件公开 / 不公开"两套规则｜旧版文档多处重复、写进过程记录，难读也难维护。
2026-10-17｜界面演示页一律做成独立的静态页，不改项目代码；技术做法到方案阶段定｜用户看第 5 阶段复盘后在两种做法里选定。
2026-10-17｜状态更新：用户每发来一条消息算一轮，开头和回复前都判断阶段和状态、该变马上改；主 Agent 和子代理之间的来往不算｜试用中出现过问完问题没改"等你"、用户回复后没改回来。
2026-10-17｜不提醒用户换新会话，由用户自己决定｜用户看第 5 阶段复盘后决定。
2026-10-17｜实现员有看不懂的地方才先问，不强制先问一轮｜试用中实现员没先问也没返工，按需先问能省一轮来回。

## 角色和模型

2026-10-09｜子代理默认：实现员 Sonnet 最新版 / sol 系列最新版，medium；验收员和评审员 Opus 最新版 / astra 系列最新版，high；找不到时继承主会话模型；用户可改｜强模型负责需求、方案和验收，低一档模型照方案实现。
2026-10-10｜主会话的模型和档位由用户自己选，coding-pal 不设默认、不要求修改｜用户 10-10 决定。
2026-10-09｜验收员默认参加需求类任务和高风险任务；小改动由主 Agent 自查｜小改动做完马上能看效果，由用户自己看。

## 验证

2026-10-06｜验证按功能影响和成本收益裁剪，普通改动只核对局部效果，不做全场景验收｜避免为小改动跑大量无关检查。
2026-10-17｜AI 案例只跑和这次改动相关的，发布前也一样；覆盖不到就补一个；全部关键案例只在用户要求"全面检查"时跑｜题目多了会越来越慢，一次发布也可能只有一个小改动。
2026-10-17｜改到 AI 行为的小改动仍按小改动做，不升格为需求，交给用户看之前跑相关案例｜用户看第 5 阶段复盘后选定：用跑相关案例代替升格。
2026-10-09｜coding-pal 自身发布前集中验证：9 个关键场景 × 2 个平台，只跑和改动相关的｜任务里轻验证，发布前集中验。
2026-10-18｜coding-pal 的场景评判默认用 Codex；Codex 额度不够时可以改用 Opus 5.5 max｜两者对同一批结果的结论一致。
2026-10-05｜不为已结束的任务长期保留测试和验收证据｜用户没有长期留档的需要，避免临时目录越积越多。

## 写作和展示

2026-10-09｜技能文字有篇幅预算（合计 25,000 字、入口 3,000、单个阶段 2,000、一次动作 8,000），超出时用户在"删并哪几条"和"提高上限"之间选｜防止规则再次只加不减。
2026-10-09｜写作规范不列停用词｜用户 10-09 确认重建方案时选定。
2026-10-18｜"不向用户引用技能原文"只是体验改进，不是强制要求；Codex 改不掉就当它固有的说法，不为此加提示词或评分要点（取代 2026-09-28 关闭的同一观察项）｜引用不影响流程和结果。
2026-10-04｜所有项目的验收网页用同一套样式；网页只用来阅读核验，反馈和最终确认在对话里｜跨项目、跨需求保持一致的阅读体验。
2026-10-17｜验收网页里要打开的网页写成可点的文字链接，在新标签页打开；"请你试"一项一行｜原来显示成路径加复制按钮，要粘到地址栏才能打开。
2026-10-10｜看板有左侧项目和任务栏、亮暗切换（跟随系统 / 亮色 / 暗色）；10-11 加上：验收网页跟随看板的亮暗，验收阶段的任务直接链到验收网页｜用户看过页面后提出。

## 发布与版本

2026-09-29｜插件照 Anthropic 官方插件市场的结构，经单独的目录仓库 `pal-plugins` 发布｜开发仓库里单独放一个目录做不到只下载必需文件。
2026-09-29｜接受 Codex 自动更新：Codex 使用者开新会话就拿到最新发布版；Claude Code 只在使用者要求时更新｜Codex 无法关闭自动刷新；使用者只会拿到已验收发布的版本，风险有限。
2026-10-01｜作者本机和其他使用者一样装发布版，不用链接版｜和使用者体验一致，日常只用已验收的版本。
2026-10-04｜版本号由 Agent 按升级影响自主定：不兼容改第一位，兼容新能力改第二位，兼容修正改第三位；项目已有版本规则优先；不请用户确认编号，定号只分析已有资料、不额外实测｜用户不想操心版本号，也要控制 token。
2026-10-04｜多个已验收任务可以合并后一起发布；合并本身不升级版本｜版本只表达实际交付。
2026-10-09｜历史版本改为 0.x（2.0.0～5.4.1 对应 0.1.0～0.8.1，对照表见 CHANGELOG），重建版为 1.0.0；取代 2026-10-04"历史版本不重新编号"｜0.x 表示还在开发、随时可能变，1.0.0 表示第一次稳定公开，正好对应实际情况。
2026-09-29｜本仓库公开时 `docs` 一起公开，旧版归档不公开；提交记录里的邮箱可以公开｜方便以后协作开发。
2026-10-01｜公开时用干净的版本历史，版本标记不推送到公开仓库，公开前加 MIT 许可证｜版本历史里有隐私内容，只在公开时有影响。
2026-10-18｜公开方式：把现有仓库换成干净历史（从 1.0.0 的一个起点提交开始）后公开；旧历史、0.x 标记和发布说明另存私有归档仓库 coding-pal-archive｜用户在"现有仓库清史后公开"和"另建公开发行仓库"之间选了前者。
2026-10-18｜公开仓库只有 1.0.0 及以后的版本标记，0.x 标记只在私有归档（Agent 按上一条细化 2026-10-01 的"版本标记不推送"）｜新标记指向干净历史，不涉及隐私；插件目录要靠标记定位版本。
