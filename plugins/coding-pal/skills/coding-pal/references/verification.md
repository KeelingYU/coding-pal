# 验证

## 每个任务

- 改到逻辑就补自动测试；修问题前，先确认测试能检出原问题。纯文案只核对显示效果。
- 实现员按方案写测试，你每组跑测试。需求类任务和高风险任务派验收员，小改动由你自查。
- 合并时 pal 跑 `.pal/config.json` 的 `checks`；发布前跑 `release.checks`。
- 说"完成"或"通过"，要有实际运行结果（命令输出、截图）。交给用户的页面，先自己在浏览器里打开看一遍；自动测试用无界面浏览器或隔离环境，不在用户的浏览器里弹页面。
- 不为通过而放宽标准或改弱测试。确实要放宽时，先告诉用户原来查什么、为什么改、以后哪些情况不再被拦住，用户同意后再改。
- 失败先分类：产品缺陷，修产品；检查本身写错了，说明后修检查，但不降低要求；环境或额度问题，记为未完成，恢复后接着做。不反复重跑直到通过。
- 临时文件（测试项目、截图、日志）只放 `pal path tmp <任务>`；合并或放弃任务时，pal 会删掉它。

## 产品里有 AI 功能时

"AI 案例"是项目里保存的一组输入，加上"应该怎样、不能怎样"的说明。"改到 AI 行为"指改了提示词、技能或子代理说明、工具设置、模型及参数、检索资料。案例和运行方法写进项目规则的"构建与测试"；`.pal/config.json` 的 `ai_cases.cost` 记成本：`cheap`（每个几分钟、少量 token）或 `expensive`（每个要真实跑一个 Agent 会话），`ai_cases.run` 写怎么运行。

只跑和改动相关的案例：

| 时机 | 便宜的案例 | 昂贵的案例 |
|---|---|---|
| 任务改到 AI 行为，交用户验收前 | 跑受影响的 | 跑 1 个最有代表性的，先问用户；用户验收时亲手试 |
| 合并时 | 不跑 | 不跑 |
| 发布前 | 这批有改到 AI 行为的任务才跑，只跑和它们相关的 | 同左，一批只跑一次 |
| 全面检查 | 用户说"做一次全面检查"时跑全部关键案例；看板提醒积累多了、或要发大版本时，建议用户做并说明代价 | 同左 |

现有案例覆盖不到这次的改动时，补一个相关的案例，和补测试一样算任务的一部分。结果由验收员按案例说明判断，不用文字匹配。做完全面检查后，把 `ai_cases.last_full_check` 改成当时的时间（例如 2026-10-12T14:20），看板据此提醒。
