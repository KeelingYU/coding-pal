# 需求阶段

把用户要的东西写成需求说明，交用户确认。这个阶段不写代码，也不和用户讨论技术选型。

## 1. 开始前

- 已有没暂停的任务在需求或界面阶段时，先请用户三选一（推荐项排第一）：
  - 等待：用 `pal todo add` 记进待开始。新需求和那个任务不相关时推荐。
  - 并进那个任务：同一块功能、同一批用户时推荐。那个任务已在界面阶段的，退回需求阶段。
  - 暂停那个任务，先做新的：新需求明显更急时推荐。用 `pal set <那个任务> 状态=暂停 原因=...` 标记。
- 确定开始新任务时，建任务：`pal new <英文短名> --type 普通需求 --title "<中文标题>"`（复杂需求把类型换成复杂需求）。在哪里改，见入口的"在哪里改"。
- 读产品说明（`pal path product <任务>`）、相关代码和项目规则。已经写明的、用户第一句话说清的，不再问。

## 2. 弄清七件事

| 要弄清什么 | 具体内容 |
|---|---|
| 为什么做 | 解决什么问题，谁在什么场景用 |
| 怎样算成功 | 验收时怎么试，看到什么算对 |
| 范围 | 做什么，明确不做什么 |
| 主要流程 | 从拿到产品到完成核心任务的每一步 |
| 规则和特殊情况 | 出错、没有数据、中途中断时，用户看到什么 |
| 限制条件 | 平台和设备、要对接的系统、数据来源、隐私 |
| 偏好与参考 | 喜欢或不喜欢的例子、已有的想法 |

同时判断有没有用户会看到的界面，有才进界面阶段。

## 3. 提问

- 每轮问 3~5 个问题，按影响大小排序。每题带推荐答案，或给 2~3 个选项，推荐项排第一。
- 主动指出遗漏的特殊情况、前后矛盾和更简单的做法。技术问题自己定，不问用户。
- 没弄清的点分三类：
  - 猜错会推翻方案的：必须问到有答案。
  - 猜错了改起来便宜的：自己定，写进需求说明的"假设"。用户说"你定"也这样处理。
  - 要看到实物才能定的：写进"留到后面再定"，注明在界面阶段还是验收时定。
- 结束提问前，用业务语言复述整个需求：一段概述、主要流程、验收时怎么试。复述完就停下等用户回复，不在同一轮接着写需求说明；用户确认复述无误，才开始写。用户的回复改了需求时，复述改后的版本，再等确认。

## 4. 写需求说明

- 先看其他没合并的任务卡片里的"影响范围"。改同一块但不矛盾：在方案里写明依赖，等对方合并后再实现。互相矛盾：告诉用户，给出选项和推荐。
- 填写任务文件夹里的 requirement.md（`pal new` 已照 `templates/requirement.md` 建好）。只写产品，不写技术实现。验收标准每条写成"做什么操作 → 应该看到什么"，包括失败时的表现。
- 作为草稿交付：用几句话讲要点，列出重要假设，请用户确认；卡片写上影响范围。
- 用户要求修改的，改完再请用户确认。

## 5. 用户确认后

1. 阶段改为界面（没有界面时改为方案），卡片写上需求摘要。
2. 在决定记录（`pal path decisions <任务>`）记一条。
3. 接着做下一阶段。
