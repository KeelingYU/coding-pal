# 方案阶段

写实现方案。技术判断全部由你做，用户只看开头一页。

## 1. 写方案

- 先读产品说明和实现说明（`pal path product <任务>`、`pal path architecture <任务>`）的相关部分、需求说明和相关代码。在现有做法上扩展，不借机重构无关的部分。
- 填写任务文件夹里的 plan.md（`pal new` 已照 `templates/plan.md` 建好）：
  - 开头一页给用户：用户会看到什么；有哪些取舍，各自的代价；要不要评审，为什么；谁来实现。
  - 技术部分给实现员：写到不知道前因后果的低一档模型照着做，也不会做错。
- 分并行组：每组只改自己负责的文件；几组都要改的文件（组件清单、导出入口、依赖清单、锁文件等）留到最后的联调步骤。
- 只有一两个很小的步骤时，由你自己实现，在开头一页说明。
- 依赖其他没合并的任务时写明，等它合并后再开始实现。
- 会改到 AI 行为（提示词、技能或子代理说明、工具设置、模型及参数、检索资料）时，`pal set <任务> 改到AI行为=是`。

## 2. 高风险就评审

批量改数据、对外发布/付款/发消息、涉及隐私、大范围重构属于高风险。用户自己点"删除"这类普通功能、只存在本机的数据、从零写的新项目，本身不算。

高风险时，`pal set <任务> 风险=高`，派评审员，告诉它需求说明、实现方案和相关代码在哪里。

- 阻断项必须改。只有第一轮有阻断项，才派第二轮；第二轮只核对这些阻断项。
- 两轮后仍有分歧，用业务语言讲清分歧，请用户裁决。

## 3. 交用户看开头一页

- 用几句话讲取舍，请用户看开头一页；卡片写上方案摘要。
- 用户在交付后回复无异议或"继续"，才进入实现；交付前说的"继续"不算。用户有异议，就改方案再请用户看。
- 通过后阶段改为实现，接着按 `stages/build.md` 做。
