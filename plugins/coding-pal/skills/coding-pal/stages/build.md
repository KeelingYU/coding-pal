# 实现阶段

按方案一口气做完全部步骤，中途不停下汇报。只有需要用户决定，或遇到你解决不了的阻塞，才停下。

## 1. 开始前

- 方案写明依赖的任务，要已经合并。主线有新的合并时，在工作副本里运行 `git merge <主线>` 同步。
- 工作副本里有没提交的改动，先提交，方便之后逐组看差异。

## 2. 派实现员

- 方案写明由你自己做时，直接做，不派实现员。
- 每个并行组派一个实现员，同时最多 `parallel_max` 个（`.pal/config.json`，默认 3）；串行的步骤交给一个实现员按顺序做。
- 告诉它：实现方案（任务文件夹的 plan.md）在哪里、它负责哪一组、工作副本路径、临时文件夹（`pal path tmp <任务>`）。
- 它有看不懂的地方会先问；你回答后补进 plan.md，再让它动手。
- 实现员都在同一个工作副本里改，不提交。不要用平台自带的隔离副本：Claude Code 的 `isolation: worktree` 从默认分支建，拿不到任务分支的改动。

## 3. 逐组检查

- 每组做完：看差异，跑这组的测试，提交。
- 各组都做完、提交后：按方案做联调步骤，默认派一个实现员；只有方案写明联调很小、由你做时才自己做。然后跑全部测试。联调中测试失败，由你判断原因：照方案能修的交回实现员，要改方案的按下面第 5 节处理。
- 测试输出存进临时文件夹，验收员会直接读，不再重跑。
- 测试怎么补、AI 案例什么时候跑，按 `references/verification.md`。

## 4. 同步长期文档

这些是任务本身的一部分，不算额外改进：

- 把长期有效的需求和设计写进产品说明和实现说明（`pal path product <任务>`、`pal path architecture <任务>`）。
- 在 CHANGELOG 的「未发布」写 1~3 行用户看得懂的变化（`pal path changelog <任务>`）。
- 第一次确定构建和测试命令时，写进项目规则的"构建与测试"（放在 coding-pal 段落之外），并填进 `.pal/config.json` 的 `checks`，合并时 pal 会跑它。

## 5. 方案不合适时

- 纯技术问题：直接改 plan.md，继续做。
- 会改变用户已确认的行为或界面：先问用户。

## 6. 做完

全部步骤完成、测试通过、产品能按项目规则运行后：阶段改为验收，接着按 `stages/accept.md` 做，不停下等用户。
