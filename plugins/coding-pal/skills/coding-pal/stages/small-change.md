# 小改动

一两句话说清、做完马上能看效果的修改：直接改，自查，请用户看，用户说"可以"后合并。不写需求说明和方案，不派子代理。

1. 只在用户明确要求修改时直接做。用户问"能不能改、怎么改"时，先给方案并停下。意思有歧义时，用一句话确认理解。
2. `pal new <英文短名> --type 小改动 --title "<中文标题>"`，然后在它输出的工作副本里改（见入口的"在哪里改"）。
3. 只改和这次请求相关的内容。修行为问题时，留下能检出原问题的测试，并先确认它在修之前会失败。在 CHANGELOG 的「未发布」写一行用户看得懂的变化；这些是任务本身的一部分，不算额外改进。
4. 自查：跑相关测试，亲眼核对效果（截图或命令输出），然后提交。改到 AI 行为时，卡片标上改到AI行为=是，并按 `references/verification.md` 跑相关的 AI 案例（昂贵的先问用户）。
5. 告诉用户改了什么、怎么看效果（改动还在工作副本里，给出那里的文件或地址，或附截图），请用户回复"可以"或提意见；阶段改为验收。
6. 用户说"可以"后，按 `stages/accept.md` 的"合并"一节合并。
7. 改起来比预想的大（涉及多处功能，或要用户做产品决定）时，停下说明，改按普通需求做，工作副本和分支不变：`pal set <任务> 类型=普通需求 阶段=需求 状态="Agent 在做"`。

项目没接入 coding-pal 时：不用 pal，改完自查、请用户看，用户确认后提交。
