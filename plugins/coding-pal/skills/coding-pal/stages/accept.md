# 验收阶段

先由验收员独立检查，再交用户验收。用户说"验收通过"后合并。

## 1. 验收员检查

- 需求类任务和高风险任务派验收员；小改动由你自查。
- 只告诉验收员：需求说明在哪里（验收标准在里面）、项目规则（运行和测试方法、约定）、工作副本路径、已跑测试的输出、临时文件夹（`pal path tmp <任务>`）。不给实现方案，也不给你的结论。
- 任务改到 AI 行为时，按 `references/verification.md` 请验收员跑受影响的 AI 案例，并按案例说明判断结果。
- 未通过的项修好后，只请验收员复查受影响的项。同一个问题修两次还没通过，就停下，用业务语言向用户说明现状和选项。
- 无法验证的项，先补条件（测试数据、运行方法）；只有人能判断的（例如好不好看），放进"请你试"。

## 2. 交用户验收

- 照 `templates/acceptance.json` 在任务文件夹写 acceptance.json，运行 `pal report <任务>` 生成验收网页。证据文件放在临时文件夹，file 写相对它的路径；长日志用 highlight 标出关键行。验收项写用户看得到的效果，不写"如实记录了限制"这类没有可见效果的流程声明。数据不合格时 pal 会说哪里要改。
- 自己打开网页核对一遍。在对话里给出网页入口、"你要做的事"和预计用时。
- 逐条处理用户意见：实现问题修好再测；需求理解错或界面不对，回到对应阶段，只重做受影响的部分；本次不修的，写明理由。处理完重新生成网页。
- 用户提出以后同类改动都要做到的要求（例如"所有组件都不用浏览器自带的界面"），写进项目规则的约定（放在 coding-pal 段落之外），告诉用户写在哪；验收员以后也按它查。

## 3. 合并

- 用户明确说"验收通过"（小改动说"可以"）后，运行 `pal merge <任务>`。`.pal/config.json` 的 `auto_merge` 为 false 时，先问用户什么时候合并。
- 没成功时照输出的"下一步"做：排队就等前一个合并完（可加 `--wait 10`）；有冲突就在工作副本里合并主线、解决后重试；检查没过就修好重试。
- 输出列出主线也改过的文件时，判断已验收的效果要不要复查，并告诉用户。
- 告诉用户结果：已在本机合并；要发布的项目，等用户说"发布"再一起发。
