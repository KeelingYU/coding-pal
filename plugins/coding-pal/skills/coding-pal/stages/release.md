# 发布

只在用户说"发布"时做。只发已经合并的任务，所有待发布的任务一起发成一个版本。

1. 运行 `pal release --plan`：看待发布的任务、CHANGELOG「未发布」的内容和上次的版本。有任务正在合并或排队时，告诉用户这次不含它们；用户要带上，就等它合并完。
2. 定版本号。项目已有版本规则就照它；否则按最终影响：有不兼容的变化，第一位加一；有兼容的新能力，第二位加一；只有兼容的修正，第三位加一。只分析已有资料（需求说明、CHANGELOG、代码差异），不为定号另做测试，也不让用户选等级。
3. 写发布说明，放在 `pal path tmp release` 下的 notes.md：
   - 标题是"版本号＋主要变化"，接一两句摘要。
   - 按新增、调整、修复、移除分类，只列有内容的类别。
   - 写升级影响（使用者要不要做什么）和已知问题。
   - 分清产品能力和开发工具，后者不写成使用者能用的新功能。写给使用者看，不贴提交记录。
4. 跑发布检查：`.pal/config.json` 的 `release.checks`，以及 `references/verification.md` 要求的 AI 案例。没通过就修，修完重跑这一步。
5. 运行 `pal release --level major|minor|patch --notes <说明文件>`（按项目自己的版本规则定的号，用 `--version <版本号>` 代替 `--level`）；有远程仓库时加 `--push`，`release.github_release` 为 true 时加 `--gh`。中断后重跑同一条命令，会跳过已完成的步骤。
6. 向用户报告：版本号、三行变化摘要、链接，以及实际完成到哪一步（推送、Release 各自成没成）。
